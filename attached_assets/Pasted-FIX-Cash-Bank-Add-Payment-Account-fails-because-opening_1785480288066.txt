FIX: Cash & Bank → Add Payment Account fails because openingBalance is sent as a string

Current error:

{
  "code": "invalid_type",
  "expected": "number",
  "received": "string",
  "path": ["openingBalance"],
  "message": "Expected number, received string"
}

The Add Payment Account form currently sends openingBalance from the HTML input as a string, while the backend/API schema expects a number.

Please fix this properly end-to-end.

REQUIREMENTS

1. FRONTEND

Before submitting Add Payment Account, convert openingBalance to a numeric value.

Examples:

"0" -> 0
"1000" -> 1000
"1250.50" -> 1250.50

Do NOT send:

openingBalance: "0"

Send:

openingBalance: 0

Handle an empty field safely according to the existing business rule, preferably:

empty -> 0

Do not use unsafe parsing that can result in NaN being submitted.

2. BACKEND VALIDATION

Inspect the payment-account API validation/schema.

Make it robust to normal form submissions.

If appropriate for the existing validation framework, use numeric coercion for openingBalance so a valid numeric form value such as "1000.50" can safely become 1000.50.

However:

- reject non-numeric values
- reject NaN
- preserve decimal balances correctly
- do not silently turn invalid text into 0

Frontend AND backend should be correct; do not fix this only by weakening validation.

Do not parse account numbers into numbers because:

- leading zeros may be significant

Same principle for IFSC: always string.
