FIX ERP PERMISSION / RBAC ENFORCEMENT — PRODUCTION-SAFE

There is a serious permission issue in the ERP.

CURRENT PROBLEM

I created a hierarchy/role and assigned an employee to that hierarchy.

Example:
Hierarchy/Role: Warehouse Manager L3

In Company → Permissions, I configured restricted permissions for Warehouse Manager.

The Permission screen currently shows:

“Warehouse Manager can open 13 of 47 pages”

The permissions were saved successfully.

The employee is also assigned to a specific warehouse/location.

However, when I log in using that employee ID, the employee can still see and access almost everything in the ERP.

This means the permission configuration is either not being resolved correctly or is not being enforced correctly.

This must be fixed properly in BOTH frontend and backend.

Do NOT solve this only by hiding sidebar menu items.

==================================================
1. DIAGNOSE THE ROOT CAUSE FIRST
==================================================

Before changing production data, trace the complete permission flow:

Employee Login
→ Employee Record
→ Assigned Hierarchy/Role
→ Hierarchy Permission Configuration
→ Authenticated Session/JWT
→ Effective Permissions
→ Frontend Navigation
→ Frontend Route Guards
→ Backend API Authorization
→ Location/Warehouse Authorization

Determine exactly why an employee assigned to Warehouse Manager can see modules that are disabled for Warehouse Manager.

Check specifically for:

• Employee hierarchy not being loaded after login
• Wrong hierarchy ID being resolved
• Employee role and hierarchy conflicting
• Administrator permissions accidentally inherited
• Missing permission records being treated as ALLOW
• Default allow behaviour
• Permission configuration saved but not read during authentication
• Old/stale permissions stored in session/JWT
• Frontend hard-coded permissions
• Frontend checking employee type instead of hierarchy permissions
• Backend checking authentication but not authorization
• API endpoints missing permission middleware
• Location assignment bypassing hierarchy permissions
• Permission cache not refreshing after Save
• Mobile navigation using different permission logic
• Direct URLs bypassing sidebar permission checks

Report the actual root cause.

Do not guess.

==================================================
2. DENY BY DEFAULT
==================================================

For normal/non-admin employees, permissions must follow:

NO EXPLICIT PERMISSION = DENY

Do not automatically grant access just because the employee is authenticated.

Administrator/Super Admin can retain full access according to the existing ERP architecture.

But Warehouse Manager and other employee hierarchies must receive only their explicitly granted permissions.

==================================================
3. VIEW PERMISSION
==================================================

The View permission determines whether the employee can access the page/module.

If:

View = OFF

Then the employee must NOT be able to:

• See the module in the sidebar
• See it in the mobile menu
• Find it through global search
• Open it through dashboard shortcuts
• Open it through quick links
• Open the URL manually
• Fetch the module's protected business data through the API

If:

View = ON

Then the page can be displayed, subject to the employee's location/data scope.

==================================================
4. SIDEBAR AND NAVIGATION
==================================================

Generate navigation using the logged-in employee's EFFECTIVE hierarchy permissions.

Example:

If Warehouse Manager can open only 13 of 47 pages, the employee should only see those permitted pages/modules.

Do not show the remaining restricted pages.

This must apply to:

• Desktop sidebar
• Mobile menu
• Dashboard shortcuts
• Search/navigation results
• Quick links
• Other navigation surfaces

Parent menu groups should only appear when at least one child page is permitted.

Example:

If Accounts contains 10 pages but the employee has permission for none of them, do not show Accounts.

If the employee has permission for only one Accounts page, show Accounts with only that permitted child page.

==================================================
5. DIRECT URL SECURITY
==================================================

Hiding menu items is NOT security.

Protect every restricted frontend route.

Example:

If Warehouse Manager has no View permission for:

Chart of Accounts

and manually enters:

/accounts/chart

the ERP must NOT display Chart of Accounts.

Show an Access Denied page or return/handle HTTP 403 appropriately.

Do the same for every protected ERP page.

==================================================
6. BACKEND API AUTHORIZATION — CRITICAL
==================================================

Backend permission enforcement is mandatory.

Every protected API operation must validate:

1. Logged-in employee
2. Employee hierarchy
3. Effective permission
4. Required action
5. Employee location/warehouse scope where applicable

Do not trust frontend permission checks.

Use the permission types already available in the Permission screen:

VIEW
CREATE / ADD
EDIT
DELETE
EXPORT / DOWNLOAD
PRINT

Behaviour:

VIEW OFF
→ Protected list/detail APIs must reject unauthorized access.

VIEW ON + ADD OFF
→ Employee can view but cannot create.

EDIT OFF
→ Update APIs must return 403.

DELETE OFF
→ Delete APIs must return 403.

EXPORT OFF
→ Export/download APIs must return 403.

PRINT OFF
→ Protected print/PDF operations must be denied.

Frontend buttons should also be hidden/disabled appropriately, but backend enforcement is mandatory.

7. WAREHOUSE / LOCATION DATA ISOLATION
==================================================

The employee is assigned to a specific warehouse/location.

Hierarchy permission and location permission must work TOGETHER.

Having permission to Stock, Sales, Production, Expenses, etc. does NOT automatically mean the employee can see every company's location.

Example:

Employee:
Hierarchy = Warehouse Manager
Assigned Location = Warehouse A

If Stock View permission is ON:

The employee should see stock belonging to Warehouse A only unless the hierarchy explicitly has company-wide location access.

The employee must NOT automatically see:

Warehouse B
Warehouse C
Head Office
Other Outlets
Other Locations

Apply location scope where applicable to:

• Stock
• Stock Ledger
• Inventory
• Production
• Sales
• Expenses
• Cash Balance
• Stock Transfers
• Warehouse operations
• Reports
• Inventory quantities
• Location-sensitive transactions
• Other location-specific ERP data

IMPORTANT:

Never trust a location ID supplied by the frontend.

Example:

If Warehouse Manager is assigned Warehouse A but manually changes an API request from:

location=A

to:

location=B

the backend must reject or safely scope the request.

The employee must not obtain Warehouse B data.

Implement safe permission refresh according to the current architecture.
