MASTER ERP FUNCTIONAL, ACCOUNTING, INVENTORY, UI & DATA-INTEGRITY IMPLEMENTATION

IMPORTANT:
Use the existing ERP and the previously generated ERP Functional/Technical Specification as the CURRENT-STATE BASELINE.

Do NOT blindly rewrite existing functionality.

First inspect the current implementation and understand the existing architecture, database, APIs, accounting engine, inventory engine, location system, permissions, reports and workflows.

Then implement the requirements below.

The ERP must behave as ONE integrated accounting and operational system.

============================================================
1. CORE ERP PRINCIPLE — SINGLE SOURCE OF TRUTH
============================================================

The accounting ledger must be the authoritative source for financial balances.

Every financial transaction must follow:

USER ENTRY
→ VALIDATION
→ DATABASE
→ ACCOUNTING POSTING
→ LEDGER
→ CUSTOMER/VENDOR/CASH/BANK
→ REPORTS
→ DASHBOARD

Do NOT allow individual screens to calculate financial balances independently if the same balance already exists in the accounting system.

The following must always reconcile:

Chart of Accounts
↔ General Ledger
↔ Customer/Vendor Ledger
↔ Trial Balance
↔ Balance Sheet
↔ Profit & Loss
↔ Cash Book
↔ Bank Book
↔ Dashboard
↔ Receivables
↔ Payables

Every debit must have a corresponding credit.

All accounting must balance exactly to the paisa.

============================================================
2. EVERY TRANSACTION MUST ENTER THE CORRECT LEDGER
============================================================

This is one of the highest-priority requirements.

Every:

Sales

Purchase Return

Journal Voucher
Expense

There must never be a situation where:

- Report shows a transaction but ledger does not.
- Customer ledger misses a sale.
- Customer ledger misses a receipt.
- Vendor ledger misses a purchase.
- Vendor ledger misses a payment.
- Cash Book differs from Cash ledger.
- Bank Book differs from Bank ledger.
- Chart of Accounts differs from ledger.
- Dashboard uses a different calculation from the ledger.

Fix the ROOT accounting flow, not merely the display.

============================================================
3. CHART OF ACCOUNTS
============================================================

Chart of Accounts is the master accounting structure.

All ledgers must belong to the correct account/group.

When a new ledger is required:

1. Search existing ledger.
2. If it exists, use it.
3. If it does not exist, create it.
4. Ask/identify the correct parent group.
5. Never create duplicate ledgers unnecessarily.

Ledger balances must flow into Chart of Accounts.

Customer and vendor ledgers must be correctly linked to the corresponding accounting structure.

============================================================
5. CUSTOMER ADVANCE / CREDIT BALANCE
============================================================

Do not incorrectly classify every negative Sundry Debtor/customer balance as a separate Customer Advance liability.

The required business behaviour is:

If customer pays more than the amount due, the customer ledger can show a negative balance/credit.

Example:

Invoice = ₹1,000
Receipt = ₹1,200

₹1,000 settles the invoice.
₹200 remains as customer credit/negative Sundry Debtor balance.

When the next sale is made, that credit can be adjusted.

The system must never double-count the advance.

Investigate and prevent duplicate "Advance Adjusted" accounting postings.

An advance/credit adjustment must have one consistent accounting treatment.

Where it is incomplete or inconsistent, fix the underlying implementation.

After all changes, provide a detailed completion report showing:

- What was changed
- What was already working
- What bugs were fixed
- What backend services were changed
- What database changes were made
- What modules were affected
- Regression test results
- Accounting reconciliation results
- Location reconciliation results
- Stock reconciliation results
- Import verification
- Any remaining issues

Do not declare the ERP complete merely because the UI works.

The final verification must prove:

TRANSACTION
→ ACCOUNTING
→ LEDGER
→ STOCK/CASH/BANK/PARTY
→ REPORT
→ DASHBOARD

all represent the same underlying data.
