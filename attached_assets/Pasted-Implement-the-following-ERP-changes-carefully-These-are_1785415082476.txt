Implement the following ERP changes carefully. These are NOT frontend-only requirements.

IMPORTANT IMPLEMENTATION RULES

Before changing anything:
1. Inspect the existing frontend, backend/API, database schema, accounting logic, RBAC/permissions, warehouse/location scoping, reports, and migrations related to each requirement.
2. Reuse existing architecture and source-of-truth tables wherever possible.
3. If a frontend change requires backend/API/database changes to work correctly and securely, implement those changes too.
4. Do not create duplicate accounting records, duplicate stock movements, duplicate ledgers, or parallel sources of truth.
5. Do not delete/reset/reseed existing production business data.
6. Do not weaken the RBAC and warehouse-scope security work already implemented.
7. Do not publish automatically. Complete and test everything in development first.
8. Avoid unnecessary schema migrations. If a schema migration is genuinely required, make it idempotent and production-safe and explain why it is required.
9. Existing DATE-column conversion/self-healing logic and /api/healthz/schema must remain intact.
10. Before completion, test frontend + API + database behavior together, not merely that pages render.

1. DASHBOARD KPI CHANGES
==================================================

On the Dashboard, remove/replace these two KPI cards:

- Invoices
- Avg Ticket

Add:

- Expenses
- Bank Balance

EXPENSES:
Show the actual expense amount for the dashboard's applicable reporting period using the ERP's authoritative accounting/expense transactions.

Do not calculate it from a frontend-only list if the accounting source of truth is elsewhere.

BANK BALANCE:
Show the actual aggregate bank balance from the accounting/cash-bank ledgers.

Do not include physical cash unless the ERP's existing definition of Bank Balance explicitly includes it.

If multiple bank accounts exist, the KPI should represent the correct combined bank balance according to the existing accounting ledger balances.

Check whether the dashboard API needs modification. If it does, update it rather than calculating financial values independently in the frontend.

Dashboard values must respect any applicable RBAC/location scope.

5. REPORTS CENTER – BRANCH / STOCK TRANSFER REPORT
==================================================

Add a new Reports Center section/tab:

"Branch Transfer"
or
"Stock Transfer"

Use the existing internal stock-transfer records and stock movements as the source of truth.

DO NOT generate fake sales invoices or fake purchase invoices.

For location-level reporting, present a completed internal transfer as:

Sending location:
Transfer Out / Sales-equivalent operational view

Receiving location:
Transfer In / Purchase-equivalent operational view

This terminology is for branch performance/stock reporting only.

DO NOT treat an internal transfer as external company revenue or purchasing.

The report should include at minimum:

- Transfer number/reference
- Transfer date
- Source warehouse/location
- Destination warehouse/location
- Item
- Batch where applicable
- Quantity
- UOM
- Unit cost
- Total cost/value
- Transfer status
- Dispatch date
- Received date
- Created/handled by, where available

Provide filters for:

- Date/date range
- Source location
- Destination location
- Item
- Status

Provide summary values including:

- Transfer Out quantity/value
- Transfer In quantity/value
- In-transit quantity/value where applicable

Completed/received transfers should count in final Transfer Out/Transfer In totals.

Pending/in-transit transfers must be separately identifiable and must not be represented as completed receipts.

Provide CSV/PDF export consistent with the existing Reports Center.

CRITICAL ACCOUNTING RULE:

Internal branch/warehouse transfers must NOT inflate:

- Company sales/revenue
- Purchases
- GST/output tax/input tax
- COGS
- Debtors
- Creditors/vendor payables

Do not double-count inventory.

The report is an internal stock-movement report.
