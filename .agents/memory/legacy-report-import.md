# Legacy report import (Migration Wizard)

- **Detection is a pre-pass in `parseWorkbookValues`** (`lib/legacyReports.ts`): scan rows 1–15 for the report family's real header-token signature (banner rows sit above; header usually row 6). Sample templates can never match a signature by design — keep it that way when adding columns. The row cap applies AFTER conversion (raw day book exceeds it before folding).
- **Sales report money semantics:** Rate is PRE-TAX; Amount is the GST-INCLUSIVE line total → unit price = Amount ÷ Qty. Unit-group separator/total rows are dropped. "WALKING CUSTOMER" → walk-in cash sale; every other sale imports as CREDIT so the receipts file settles it.
- **The old software reuses document numbers.** Same "Invoice No" names several bills (different date/party) — renumber with /2, /3… suffixes keyed by a LOOKUP of (number → date+party variants), never a consecutive-run rule: one bill's rows are scattered across unit sections. Receipts/payments reuse voucher numbers the same way (/2 dedupe).
- **Payment-mode mapping:** NEFT/HDFC/TPT → Bank, UPI → UPI, blank → Cash. The UPI mode needs a cash-bank ledger with "UPI" in its name or the row errors with instructions telling the user to create one.
- **Non-party names route, never drop silently:** receipt/payment rows against capital/expense heads surface as `routable` in the mapping step — targetKind `'ledger'` imports as a journal voucher (shared journal create path, stamped with legacy voucher number + batch id, JV-aware rollback) or `'skip'` (target_id 0, listed in the skip report, excluded from money totals). Purchase charge lines (e.g. PACKING AND TRANSPORT) map with targetKind `'charge'` → bill charge owed to the vendor, never stock.
- **Day book keeps ONLY Journal/Contra** after date fill-down and multi-leg folding. The owner's real file contains zero of those → the converter returns an informative error listing every excluded voucher type ("covered by their own files") — that error is the CORRECT outcome, not a bug.
- **Wizard approve is ONE transaction for EVERYTHING:** the status claim, location restamp + revalidation, documents, row outcomes, batch statuses and the final migration status all commit atomically (advisory lock serialises attempts outside the txn); any failure rolls back everything, leaving the migration demo_ready exactly as the demo left it — never let the claim/restamp/revalidation or post-COMMIT bookkeeping live outside the boundary, or a failure strands partial state. Dev-only `IMPORT_FAULT_INJECT=approve_revalidation|approve_bookkeeping` env hooks fault-inject to verify this.
- **"One transaction" is only as true as the helpers:** any helper the import path calls that reads via the shared pool uses a DIFFERENT connection and cannot see transaction-local state — the doc gets priced against a different database view. Thread the caller's client (`q`) into every read the import path performs — document writers AND the whole validator stack approve re-runs (mappings, masters, ledgers, existing documents, stock, settings, location names); transactional-view tests (create data in-txn, import/revalidate, assert it was observed, rollback leaves state unchanged) lock this in.
- **A failing suite may predate a redesign, not your change:** several import suites still test the retired auto-create/resolve-step flow and fail against the mapping-first wizard. Baseline the suite against HEAD (git stash + rebuild + rerun) before treating it as your regression.
